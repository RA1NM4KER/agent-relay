    fix(codex): reuse Codex's own shared daemon instead of --remote (agent-relay#18)
    
    Root cause, live-verified against codex-cli 0.155.0's own source at the
    matching release tag: the event-driven runtime spawned a private
    `codex app-server --listen unix://...` and appended `--remote <endpoint>`
    to the interactive command so it would attach to that private runtime.
    Codex's own TUI puts any `--remote`-launched client in
    `ThreadParamsMode::Remote`, and explicitly strips every permission field
    (approval_policy, sandbox, permissions, permission-related `-c` overrides)
    from a `thread/resume` request in that mode -- "resuming restores the
    server's saved permission settings", per the TUI's own source comment --
    rejecting the request outright first if the CLI explicitly asked for an
    override. A real dogfood session hit this directly: `--yolo` plus
    `--remote` was rejected with "Permission overrides are not supported when
    resuming a remote task."; dropping `--yolo` let the resume proceed but
    under Codex's non-yolo default, breaking previously-unattended MCP writes.
    
    Fix: `ensure_managed_daemon` (relay-provider-codex::runtime) runs
    `codex app-server daemon start` -- the same officially supported shared
    local daemon `codex agents` already relies on for multi-client access --
    and returns its well-known control-socket endpoint. The event runtime
    attaches its own observer to that daemon instead of a private one, and the
    interactive `TerminalCommand` is never modified: no `--remote`, nothing
    else appended. An ordinary local `codex resume` with no `--remote` flag
    auto-discovers and reuses that exact same daemon on its own
    (`ThreadParamsMode::Embedded`, not `Remote`), so every already-resolved
    provider argument -- `--yolo` included -- keeps meaning exactly what it
    always did. Relay never owns or terminates this daemon: it is shared and
    Codex-owned, and must keep running after this session ends.
    
    Removes the now-superseded "Relay owns and must reap its private
    app-server" machinery (CodexRuntimeRecord/StaleReconciliation/
    reconcile_stale/terminate_orphan and the durable runtime-record file) --
    there is no longer a process Relay itself spawns and must reap. The
    executable-resolution fix this depends on (event runtime reusing the
    terminal's already-resolved executable) was already fixed and merged
    separately (1668a88); this change does not touch it.
    
    Tests: ensure_managed_daemon parses the documented daemon-start JSON and
    fails closed on a missing/failing executable or malformed output; a
    resume's argv with event-driven mode on is byte-for-byte identical to
    event-driven mode off, including a persisted permission-affecting
    argument (--sandbox); the existing executable-resolution regression is
    updated for the renamed trace event and now also asserts unmutated argv.
    Observer attach/reconnect tests are unchanged and still pass -- they test
    the protocol against a disposable AppServerHandle-spawned app-server,
    independent of which app-server the production path now uses. Polling
    (GitHub #13) is untouched.
    
    Full `cargo test --workspace` is green except pre-existing, already-
    documented m6_auto.rs timing flakes under full-workspace parallel load
    (three different, unrelated tests have each flaked once across three
    separate full-workspace runs this session; every one passes reliably in
    isolation) -- not touched, per instruction not to chase unrelated flakes
    in this change.
    
    Does not close agent-relay#18: periodic polling (#13) is intentionally
    still active, and this has not yet been validated against a real natural
    exhaustion end-to-end.

    feat(codex): close event-attribution for simultaneous sessions and suppress periodic polling while healthy (agent-relay#18)
    
    The previous audit's one remaining blocker: Codex's app-server protocol
    broadcasts thread/started to every client sharing a CODEX_HOME, with no
    client/session-scoped filter anywhere in the protocol (confirmed
    exhaustively against the generated schema: 170 client request methods,
    84 server notifications, none scoped by identity). Two live Relay
    sessions sharing one Codex profile could therefore misattribute each
    other's threads during event-driven observation — a configuration this
    project's own history shows actually happens.
    
    Closes it architecturally, not by guessing: EventDrivenRuntime::start
    now acquires a new relay_core::handoff::ProfileSessionLock (a genuine
    flock, not a pid file) for the exact CODEX_HOME before doing anything
    else, making "at most one live Relay-managed session observes this
    profile's events at a time" a provable invariant. A second session is
    refused visibly and falls back to ordinary polling-only supervision.
    
    Two issues surfaced and fixed during the adversarial pass:
    - an initial join-based stop() implementation made ordinary shutdown
      take as long as a full attach-retry timeout (15s, live-measured);
      fixed by moving the lock's ownership into the worker thread's own
      closure while attaching, and back onto the runtime struct on success,
      so stop() stays fast while the invariant still holds without a join.
    - the lock leaked a heap allocation and an open fd on every *refused*
      acquisition, not only successful ones (caught by an independent
      adversarial review); fixed by testing the lock locally before ever
      needing a 'static guard, so nothing is leaked on either path.
    
    With exclusivity provable, CodexPollScheduler can now suppress its own
    periodic timer while the observer is proven healthy — zero periodic
    account/rateLimits/read calls, never just a long interval — while still
    responding to a real usageLimitExceeded event or a post-reconnect
    reconciliation read exactly as before. The moment health can't be
    confirmed, the ordinary adaptive timer resumes immediately and visibly.
    An operator's own explicit RELAY_CODEX_POLL_SECS override is left alone
    regardless of health.

    fix(core): keep ProfileSessionLock's explicit unlock, fix its leak-on-refusal without it (agent-relay#18)
    
    The previous commit's ProfileSessionLock forgot its fd_lock guard and
    relied on closing the underlying File to release the flock implicitly.
    CI's macOS runner proved that unreliable: a held lock stayed held even
    after the holder was dropped (crates/relay-core/src/handoff/lock.rs's
    own a_profile_lock_is_acquired_when_free_and_refused_while_held test
    failed there, though it passed 50/50 locally). Reverting to keeping
    fd_lock's own guard alive — whose Drop issues an explicit flock/LOCK_UN
    call rather than relying on close-implies-unlock — fixes it.
    
    That reintroduces the leak-on-refusal bug the guard-forgetting version
    was fixing: Box::leak-ing before attempting the lock means a *refused*
    attempt leaks too. Fixed instead with a cheap, non-leaking probe first
    (a throwaway, un-leaked RwLock that tests the real lock and explicitly
    unlocks before returning) — only once that confirms the lock is free
    does this leak a Box and re-acquire for real. A narrow race remains
    between the probe's release and the real acquisition, but that only
    costs a leak in a genuine, rare race, never on an ordinary "already
    busy" refusal.
    
    Also loosens the leak-detection test's assertion from exact equality to
    a tolerance: it reads /dev/fd, which reflects the whole test process,
    and other tests running concurrently on their own threads produced
    enough cross-test noise to make exact equality itself flaky.

    An independent review of commit 75ba067's rollout.rs found two concrete
    correctness gaps, both now fixed:
    
    1. A file created after RolloutWatcher::attach, with records (including a
       usage_limit_exceeded one) already written before the background loop's
       first lazy discovery, could have its baseline computed from the file's
       raw current length at the wrong moment, or from a stale/impossible
       durable offset, silently skipping content this exact watcher never
       actually read:

         back to the safe baseline instead of clamping) unless its path AND
         device/inode AND offset-no-larger-than-current-length all hold —

         the same path, and never a blind clamp of an offset the file has
         since shrunk past.
       - Baseline::ExistedBeforeWatch's fallback is now the file's last
         *complete* line boundary, never its raw byte length, so a record
         only partially written at the exact instant attach()'s one
         synchronous stat runs can no longer be torn in two and lost.

       end-to-end test proving the full chain a real rollout exhaustion record
       takes through to the scheduler: rollout event ->
       codex_usage_limit_event_received -> exactly one triggered evaluation,
       with zero periodic reads while healthy throughout.

    (every worker_loop exit path, via the HealthGuard drop guard) and
    exit/recovery semantics were already sound; only the baseline/offset

    A second, concurrent Relay-managed operation on the same Codex profile (a fresh `relay codex`
    launch, or a handoff/switch/automatic-handoff bootstrap target) could create a real thread via

    into a profile-domain one: a live supervised Codex TUI can change which native thread it drives

    own forked_from_id, /new and "resume a saved chat" via post-watch growth on another structurally
    top-level rollout, attributable to the one supervised TUI because no other Relay-controlled
    operation can be driving a top-level thread on this profile while it holds the lock. Subagents and
    ephemeral side-conversations are excluded structurally, never by heuristic.
