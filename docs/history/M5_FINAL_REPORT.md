## 9. How Herdr plugin assets work outside the source checkout

This was M3's explicitly documented, unsolved packaging gap. Fixed (M5.5): the plugin manifest
(`crates/relay-herdr/assets/herdr-plugin.toml.template`) is embedded into the `relay` binary via
`include_str!`. `relay integration herdr install` (and `relay setup`'s Herdr step) materializes it
into `<config_root>/herdr-plugin/herdr-plugin.toml`, substituting the placeholder for the absolute
path of the `relay-herdr-plugin` binary — located as a sibling of the running `relay` executable
(true for both a Homebrew/release install and a local `cargo build --release`), falling back to a
`PATH` search. `herdr plugin link` (not `install`) is what actually gets invoked against that
materialized directory — no `[[build]]` step, since the binary is already built. An explicit
`--plugin-path` still works unchanged for the source-checkout/dev case. **TEST VERIFIED** at both
the `relay-herdr` unit level (`resolve_plugin_path_with_override_materializes_the_embedded_manifest`,
plus a structural-diff test asserting the embedded and repository manifests never silently drift
apart) and the `relay-cli` integration level (`crates/relay-cli/tests/m5.rs`, running the real
`relay` binary from a cwd with no `plugins/herdr` anywhere near it). **LIVE VERIFIED** in §7.

## 14. macOS signing/notarization findings

**RESEARCHED, DEFERRED, LIVE-CONFIRMED WORKING UNSIGNED.** Both the locally-built binary and the
real Homebrew-installed binary (`/opt/homebrew/Cellar/agent-relay/0.2.0/bin/relay`) carry no

via a Homebrew-driven `curl`, was tested (§7); neither picked up a quarantine attribute (unlike a
browser download, which would). Conclusion: unsigned custom-tap installation works normally on
this real system; signing/notarization is deferred, matching the task's own default when this is
true — no Apple Developer certificate was purchased or requested.

## 17. Security/supply-chain audit

- **CI has never been green on GitHub's hosted runners for this entire project, discovered and
  fixed this session** — see §18, the single largest finding of M5. Every `cargo test --workspace`
  run on `origin/main` since before v0.1.0 shipped had actually been failing; this was invisible
  locally because none of the four root causes reproduce on this development machine.
- Workflow permissions are minimal: `permissions: contents: read` at the top of both workflows;
  `release`'s `contents: write` is scoped to that one job only (needed to attach release assets),
  never granted workflow-wide.
- Third-party action pinned to an immutable commit SHA: `softprops/action-gh-release` (not a
  GitHub-owned action) is referenced by the exact commit its `v2` tag currently points to
  (`3bb12739c298aeb8a4eeaf626c5b8d85266b0e65`), not a mutable tag. First-party `actions/checkout`,
  `actions/upload-artifact`, `actions/download-artifact` are pinned to stable major versions
  (standard practice for GitHub's own actions).
- No secrets are referenced anywhere in either workflow; release publishing uses the ambient
  `GITHUB_TOKEN`, nothing custom.
- Release archives contain exactly `relay`, `relay-herdr-plugin`, `LICENSE`, `README.md` — no
  target/, no `.cargo`, no developer home paths, no auth/config/state directories, no transcript
  or session files (confirmed by inspecting the workflow's packaging step and by extracting and
  listing the real downloaded archives in §3/§7).
- The Homebrew formula's SHA-256 values are the exact ones computed by the release workflow and
  independently re-verified (§4/§7) — not hand-typed, not copied from an untrusted source.
- No secret or credential-bearing file was committed; the privacy discipline established in M1–M4
  (synthetic profile names/UUIDs only in fixtures, real profile names never in tracked files) was
  maintained throughout this session's live testing.

## 18. Tests passing

**313/313, 0 failed**, workspace-wide, on this development machine — and, for the first time,
**green on GitHub's own hosted runners too** (both `macos-latest` and `ubuntu-latest`), after four
genuine, deterministic, previously-undiscovered environment-dependent bugs were found and fixed
this session (none are the known intermittent `untracked_writer_detected` race, and none were
patched without a clear, reproduced root cause):

1. `ps -Eww` (used by `SystemProcessLister`'s real liveness/conflict-resolution safety check) is
   refused outright by GitHub's hosted macOS *and* Linux runners' sandbox (`ps` exits 1, no
   output) — confirmed via a throwaway diagnostic workflow. Two tests that called it for real now
   skip (not fail) when the sandbox itself refuses it; production behavior (fail closed on a
   genuinely unavailable `ps -E`) is unchanged.
2. `relay setup`'s interactive-wizard test assumed a real `claude` binary is always reachable on
   `PATH` — true on this dev machine (which has one), false on a bare CI runner. Fixed by having
   the test drop a `claude`-named fixture onto an injected `PATH` prefix.
3. `FakeClaude`'s `--bg` output used `printf '...\xc2\xb7...'` — a bash/ksh-only hex escape;
   Ubuntu's `/bin/sh` is `dash`, which prints that sequence literally instead of the UTF-8 bytes
   Relay's real `backgrounded · <id>` parser expects. Replaced with the POSIX-portable octal form
   (`\302\267`), confirmed byte-identical under both `bash` and `dash`.
4. (Found via this session's own dogfooding, not GitHub CI) A Herdr-plugin-binary-discovery test
   assumed the ambient `PATH` never contains a real `relay-herdr-plugin` — true until this
   session's own `brew install` put one on this machine's real `PATH`. Fixed by threading the
   `PATH` value through as an explicit test parameter instead of reading the real environment.

## 24. Can a stranger install and run Agent Relay from three commands?

**Yes, live-verified.** `brew install RA1NM4KER/tap/agent-relay`, `relay setup`, `relay claude` —

packaging can control.
